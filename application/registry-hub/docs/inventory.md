# Image inventory

The management API exposes a persistent inventory of observed references, manifest content, and cache objects. All inventory routes require the existing `task-admin` permission. They use the management listener and authentication settings described in [security.md](security.md).

| GET endpoint | Result |
| --- | --- |
| `/api/v1/images` | Reference inventory; use `scope=platform` for independent manifest content |
| `/api/v1/images/summary` | Counts by scope and category, plus coverage and freshness |
| `/api/v1/images/status` | Live backfill phase, committed cursors, active task/image, progress time, and retry state |
| `/api/v1/images/{imageID}` | Binding, lifecycle, classification, and evidence |
| `/api/v1/images/{imageID}/platforms` | Descendant manifests, including artifacts with no known platform |
| `/api/v1/images/{imageID}/objects` | Deduplicated manifest/config/layer closure |
| `/api/v1/cache/objects` | Cache objects, including blobs without known manifest associations |

Lists accept `limit` (default 100, maximum 1000), `token`, and an optional `snapshotID`. Image lists support exact `category`, `authority`, `repository`, `reference`, `digest`, `platform`, `cacheState`, and `executionState` filters. Cache lists support `authority`, `repository`, `digest`, `cacheState`, `associated`, and `cleanupPending` filters. Each enum filter accepts one complete value; joined values such as `complete|partial` return 400. Booleans use `true` or `false`.

```sh
curl -u "$ADMIN_USER:$ADMIN_PASSWORD" "$ADMIN_URL/api/v1/images?category=cached_not_started"
curl -u "$ADMIN_USER:$ADMIN_PASSWORD" "$ADMIN_URL/api/v1/images?scope=platform&platform=linux/arm64/v8"
curl -u "$ADMIN_USER:$ADMIN_PASSWORD" "$ADMIN_URL/api/v1/cache/objects?associated=false"
```

Use returned `nextToken` values unchanged. Tokens bind the filters and immutable snapshot, expire after at most 15 minutes, and allow changing the page size. Details and child lists accept `snapshotID` to inspect the same observation. Invalid queries return 400, missing image IDs return 404, and expired explicit snapshot IDs or tokens return 410. Requests for the latest inventory return 503 with `Retry-After` when the current snapshot has expired; inspect `/api/v1/images/status` for background progress. An unavailable core index also returns 503. Responses use the existing management error envelope.

## State interpretation

The status endpoint reads background progress independently of the published snapshot and accepts no query parameters. It is available during initial backfill, including before the first nonempty snapshot. Its `batch` fields report the latest committed batch's start time, completed steps, and observed storage operations before that checkpoint was written; the operation count excludes the checkpoint write itself. An empty partial snapshot does not establish that physical inventory is empty. Status queries never advance or repair the builder.

`cache.state` measures verified cache availability independently of Distribution. Its values are `complete`, `partial`, `none`, and `unknown`. `availability.state` measures the union of cache and verified local Distribution objects. Counts and bytes describe a deduplicated logical closure within one scope; totals across images are not physical storage usage.

Categories follow this priority: `solidified`, `cached_not_started`, `solidifying`, `failed`, `cancelled`, `cached_start_unknown`, `waiting_cache`, `not_scheduled`, and `unknown`. Solidified content requires a complete verified closure and durable anchor evidence for the current content generation and GC epoch. A tag also requires a confirmed local binding. A successful task or a manifest HEAD response alone does not establish solidification. One platform can be solidified while its parent index remains incomplete.

`solidification.started` is tri-state. A reliably registered new lifecycle starts at `false`. Before local validation, transfer, or publication, the worker durably records an execution fact; background projection copies its original time into lifecycle records. Failure to persist that required fact defers execution; failure of its inventory projection retries independently. Queueing and upstream discovery do not count as starting. Active work with delayed execution projection must not be interpreted as `cached_not_started`. Historical scopes without reliable start evidence report `null` and `legacy_start_unknown`. Retries and GC do not reset the first start time. A tag binding revision and digest content generation have separate lifecycle identities.

Unknown platforms remain null. Referenced attestations and other artifacts remain part of an index closure. A manifest's subject association is metadata and does not implicitly expand the dependency closure. Locally pushed repositories without an upstream authority use an empty `authority` and their original repository name.

## Storage and refresh

Manifest responses and solidification discovery do not synchronously project inventory associations. Requests first commit verified cache data and authoritative discovery observations, including their original confirmation time and generation. An optional enqueue has a five-second budget and a fixed number of storage operations, independent of descriptor count. A failed enqueue does not fail an otherwise committed request. Independent paged scans of tasks and verified cache metadata recover missed work, including after restart. Graph handoff and the existing inventory source scan remain additional recovery paths.

Durable jobs under `background/v1/` cover manifest projection, execution facts, committed-download cleanup, blob notifications, and individual root wakes. Jobs use conditional creation, versioned checkpoints, one-minute processing leases, and fencing. Each projection unit handles one association or descriptor; shared-blob execution walks demands and graph nodes with saved cursors. Replays preserve source observation times and earliest known execution times. Delayed events cannot roll back newer bindings or generations. Completion receipts deduplicate replay; execution receipts retain historical source facts, while other receipts are eligible for cleanup after 30 days.

Unprojected manifests are retained until content and associations have been saved for their current generation. Deleted or superseded generations do not retain obsolete cache data indefinitely. A missing or corrupt source leaves explicit failed work for investigation and retry. A snapshot records `projectionPending` and `projectionObservedAt` at a bounded publication checkpoint. Pending inventory or execution jobs produce partial coverage with `background_projection_pending`; continued arrivals do not prevent publication. These fields describe that checkpoint, not a live transaction across queues and sources.

Source scans retain bounded page keys and offsets alongside opaque storage continuation tokens. Graph projection captures node versions, reads each root's dependency edges once into temporary parent indexes, and processes children in descriptor order. A changed node or task causes revalidation and replay; incomplete child sets never become known closures. Temporary graph indexes are removed after projection.

Image closure traversal, object verification, task-history selection, platform completion, immutable payload capture, and final link validation persist their own progress. Local historical audits hash Distribution content in 4 MiB ranges, checkpoint the hash state, and validate content generation and GC epoch before recording proof. Unsupported or invalid range responses cannot establish verification.

Each successful work step commits its cursor. Batches limit work steps, observed storage calls, and elapsed time, reserving time for checkpoint commits. Normal budget yields do not count as projection failures or enter failure backoff. Genuine storage failures resume from the last committed step. A new leader fences publication before adopting an unfinished build; completed immutable pages remain reusable. Retention protects the active build and advances independently of source scans. Task cleanup preserves its full-handoff requirement and can return without deleting a graph while its durable handoff is still progressing.

Inventory records, restart checkpoints, and immutable snapshot pages use `inventory/v1/` in the existing backend store. No additional database, bucket, or service is needed. A fenced builder lease coordinates replicas. Task cleanup hands off durable content and anchor facts before deleting the graph; lifecycle and inventory facts survive task retention.

Before removing root or blob task history, cleanup also checkpoints its demand scan and completes any execution projection that still needs those demands or graph nodes. This handoff can advance one leased execution unit itself; storage failures retain the source for independent retry. A delayed shared-blob projection therefore cannot lose its only root/platform association to task retention.

Successful source writes request a refresh. Periodic scans recover missed notifications and crashes. Discovery reads cache metadata, task graphs, and the authenticated internal Distribution catalog/tags API. Bounded local manifest reads can discover dependencies; the inventory never fetches missing upstream content. Catalog/tags cannot enumerate historical untagged manifests that have lost all other associations. Responses explicitly include `untagged_history_not_enumerable`; coverage applies only to discoverable sources. Orphan blobs expose their object identity without inventing an image name.

During initial backfill, responses expose `coverage=partial` and `building=true`. Queries only read published snapshot records. They do not call Distribution or upstreams, create reader pins or tasks, change protection owners, or clean caches. A stale snapshot retains the classifications observed at its reported time; it does not claim current success. After a generation or GC epoch change, old proof cannot establish solidification until current verification and anchor evidence exists. Read failures and corrupt or missing cache payloads carry stable reason codes.

The leader checks current availability between batches and during idle periods. It renews empty initial backfill placeholders before expiry, publishing a new immutable snapshot ID while retaining the observation boundary and unfinished build progress. Refresh retries use an independent bounded budget and exponential delay up to one minute; they do not enter projection failure backoff or count as completed inventory publication. Expired completed snapshots retain their original identity, observation time, and deadline until a real build publishes a replacement. Old snapshot IDs and tokens keep their original expiry even after a placeholder refresh or restart.

Snapshot construction captures immutable records before assembling list pages. Each image becomes a ready member only after its object and platform-link pages are durable. A persistent dependency queue includes resolved reference roots and descendant manifests, even if they arrive after the initial content scan. Missing source content produces an unknown platform member with closure reasons and any known descriptor metadata. Every such member appears once in platform lists and counts.

After dependency completion, the builder seals capture and validates links while assembling pages in checkpointed batches. Assembly retries reuse captured records and committed pagination progress. Both complete and partial snapshots require all platform links to resolve within the same snapshot before publication; a failed build leaves the previous published snapshot available. New source observations are picked up by a later build. Published snapshots remain immutable throughout retention.

## Background work management

`GET /api/v1/images/status` includes `background.queues`, `background.maintenance`, `background.statistics`, `background.health`, the current snapshot observation, and outstanding download quota. Queue summaries expose counts by state, oldest source age, checkpoint progress, retry count, next attempt, and the latest error's entity, phase, time, and recovery status. Cleanup summaries include pending reserved bytes. These summaries are asynchronously observed; check their observation time, `complete`, `stale`, and `readErrors` before interpreting missing or old values. GET requests use fixed summary reads and never run a full queue scan or repair work.

| Endpoint | Purpose |
| --- | --- |
| `GET /api/v1/background/{kind}?limit=32&token=...` | A bounded page of active job headers; maximum page size 32 |
| `GET /api/v1/background/{kind}/{jobID}` | A job or retained completion receipt, including source payload and checkpoint |
| `POST /api/v1/background/{kind}/{jobID}/retry` | Return failed or retry-wait work to pending; responds 202 |

Kinds are `inventory`, `execution`, `download_cleanup`, `notify`, and `wake_root`. These routes require `task-admin`; they do not retry actual solidification tasks. Failed jobs retain their source and error. Temporary failures use exponential backoff with jitter, capped at five minutes before jitter. Missing or corrupt sources require intervention rather than continuous retries.

Workers share a two-unit concurrency budget and paced admission of ten units per second per backend. Queue and source scans use bounded pages, independent cursors, and deadlines. A large entity or failed notification target does not prevent other categories or targets from progressing. The inventory projection queue applies an observed 10,000-job soft high-water mark to optional enqueue; durable source scans recover deferred work after the backlog falls. This limit and local budgets are per backend, not a cluster-wide storage rate guarantee.

Routine refreshes consume a durable change journal and retain their buffered sources, graph capture identities and dependency fanout cursors across restart. Graph updates coalesce per root and require graph projection even when the task revision is unchanged. Successful projection acknowledges only its captured graph and task revisions. Each fanout batch contains at most 128 changes and visits image fragments in pages of 32. Journal reads, acknowledgements and independent dependency reads run at most four operations concurrently. Acknowledgement retires only the exact captured source revision; a newer source revision remains pending. Cache availability, generation, proof, execution and binding changes invalidate affected image revisions. Dirty records and fragment updates reject an older builder fence. The builder still enumerates projected inventory and assembles complete immutable snapshots; unchanged entities reuse captured fragments after checking source versions and listing membership. Payload fingerprints, closure limits, content and binding identities, and GC epoch remain mandatory checks. Reuse retains the original evidence observation time. Its age is limited by the stale threshold and the greater of five minutes or the refresh interval. Fragments exceeding 8 MiB, 4,096 object dependencies or 256 listing dependencies fall back to ordinary inspection without limiting inventory results.

Full source reconciliation runs initially and becomes due five minutes after completion, or at the configured refresh interval if that interval is longer. Confirmed client manifest publications record a durable catalog notification that requests reconciliation on the next refresh. The builder checkpoints that requirement before retiring the notification, so discovery survives restart without waiting for the periodic deadline. An observed change-marker failure requests an earlier full reconciliation and increments `inventory_change_marker_failed` on `registry_hub_events_total`. A source write keeps its original success or failure even if its optional marker cannot be saved within five seconds. Cross-process interruptions and missed markers remain possible; an empty journal is not proof of complete source coverage. Status exposes the next full reconciliation, incremental phase and offsets, and fragment validation progress. Fragment records are independent optimization metadata; snapshots contain their own copies and remain valid when fragments expire. Resumable maintenance removes fragments older than snapshot retention with conditional deletion. Source history, dirty revisions and lifecycle records retain their existing identities.

Startup representation-index rebuilding remains synchronous: safe background rebuilding first requires per-entity read fallback and protection against concurrent index changes.

Cache inspection checks complete markers, size, and payload version without rereading layers. Filesystem stores use a fingerprint captured at verified cache write time; historical data without that fingerprint remains unknown until normal cache verification establishes it. Bounded historical manifest reads may recover closure metadata without creating reader pins. When previous local verification is unavailable, the background builder can stream and hash existing Distribution content once, persisting that audit separately from task observations. A complete locally verified closure and a confirmed published tag establish durable publication proof. This audit never marks a solidification lifecycle as started.

| Helm value under `backend.inventory` | Environment variable suffix after `REGISTRY_HUB_INVENTORY_` | Default | Bounds |
| --- | --- | --- | --- |
| `refreshSeconds` | `REFRESH_SECONDS` | 30 | 5–3600 |
| `staleSeconds` | `STALE_SECONDS` | 120 | At least refresh interval, at most 86400 |
| `snapshotRetentionSeconds` | `SNAPSHOT_RETENTION_SECONDS` | 3600 | 900–604800; greater than stale threshold |
| `batchSize` | `BATCH_SIZE` | 100 | 1–1000; bounds source page keys and work steps per batch |
| `batchTimeoutSeconds` | `BATCH_TIMEOUT_SECONDS` | 60 | 1–600 |

The builder processes bounded batches, persists scan cursors, and retries failures with exponential delay up to five minutes. Snapshot age starts at build start rather than publication, so a slow scan cannot make old evidence appear newly observed. Retention starts at publication so a slow build still provides a usable pagination window. Expired snapshots are removed in resumable batches. Maintenance checks its remaining budget before each cleanup unit, reserves at least twice the longest unit duration observed in that pass, and cycles through snapshot, work and fragment retention to preserve progress. Normal yields increment `inventory_maintenance_budget_yield`; storage failures increment `inventory_maintenance_failed`. Placeholder refreshes use separate `inventory_placeholder_published` and `inventory_placeholder_refresh_failed` events. These labels appear on `registry_hub_events_total`. Superseded terminal task projections are removed after 30 days once the original task is gone; the latest outcome and independent content, lifecycle, and anchor facts remain. Responses include at most 32 related task records, prioritize active work, and report `taskCount` and `task_history_truncated` when more history exists. Full current task diagnostics remain available through the task API.
