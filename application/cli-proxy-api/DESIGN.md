# CLIProxyAPI Helm Chart Feasibility Assessment and Implementation Plan

## 1. Document status

- Target directory: `application/cli-proxy-api/`
- Scope of this stage: feasibility assessment and implementation design
- No Helm chart templates will be created at this stage, and nothing will be deployed to Kubernetes.
- CLIProxyAPI evaluation baseline: `v7.2.80`, commit `09da52ad`
- Reference application: `application/sshpiper/`, `application/codespace/`, `application/sub2api/`
- Original deployment manual: workspace root directory `CLIProxyAPI_DEPLOYMENT_GUIDE.md`

## 2. Final conclusion

CLIProxyAPI can be packaged as a Helm chart. The adopted architecture is:

```text
Helm values (non-sensitive configuration)
  -> ConfigMap: config-base.json

Secret (sensitive fields only)
  -> api-keys

ConfigMap + Secret
  -> init container: render-config
  -> emptyDir: /runtime/config.yaml

client
  -> User-managed Traefik HTTPS Ingress
  -> ClusterIP Service :8317
  -> Single-replica CLIProxyAPI Deployment:8317
       |- /runtime/config.yaml (generated by init container)
       `-/data/auths (PVC, OAuth dynamic state)
  -> xAI OAuth / xAI API
```

Core decisions:

| Topic | Plan |
| --- | --- |
| Runtime image | Maintain a lightweight derived image based on the upstream CLIProxyAPI image |
| Operations scripts | Include them directly in the derived image |
| Application port | Fixed at `8317`; no values option is exposed |
| Non-sensitive configuration | Controlled by values and rendered as a ConfigMap baseline |
| Sensitive configuration | The Secret stores only sensitive fields such as the CPA API key; it does not store the complete configuration file |
| Complete configuration | The init container merges the ConfigMap and Secret into `config.yaml` in an `emptyDir` |
| OAuth state | Persist it on a PVC; a Secret volume cannot be used instead |
| Initial OAuth | After installation, start device login through `kubectl exec -it` and authorize manually in a browser |
| Ingress | Standard Kubernetes Ingress for Traefik, with a template based on `sub2api` |
| TLS | Fully managed by the user's existing Traefik/Ingress configuration; the chart does not create certificates |
| Workload | Single-replica `Deployment`, `Recreate` update strategy |
| Shared templates | Depend on bitnami common `2.x.x` |

## 3. Source code basis

The solution is based on the following behavior in the remote CLIProxyAPI source code:

1. The upstream provides `docker.io/eceasy/cli-proxy-api` multi-architecture images and releases fixed versions according to Git tag.
2. `config.example.yaml` supports explicit `auth-dir`, which can be fixed to `/data/auths` in Kubernetes.
3. `internal/cmd/xai_login.go` and `sdk/auth/xai.go` use xAI device authorization flow, output the verification URL and user code and wait for manual authorization.
4. `sdk/auth/filestore.go` writes the OAuth credentials as a `0600` JSON file to the authentication directory.
5. `internal/auth/xai/xai.go` supports refresh token to refresh access token.
6. After the token is refreshed, the updated authentication data will be persisted, so the authentication directory must be writable.
7. `internal/runtime/executor/xai_executor.go` uses `using_api` in the authentication record to determine the xAI route for OAuth requests.
8. CLIProxyAPI uses YAML configuration; JSON is a compatible subset of YAML. During implementation, the fixed-version image must still be used to verify that the configuration loader can read the generated JSON content.

## 4. Maintained runtime image

### 4.1 Purpose

The first version maintains a container image based on a pinned upstream release. It adds only the tools and scripts required for deployment; it does not modify CLIProxyAPI source code or replace the upstream binary.

Image responsibilities:

- Preserve the upstream `/CLIProxyAPI/CLIProxyAPI` binary and default startup command.
- Install `jq` for structured JSON/YAML configuration generation and OAuth JSON updates.
- Include `cli-proxy-api-render-config`.
- Include `cli-proxy-api-xai-login`.
- Optionally include a non-sensitive diagnostic script, but never output tokens or API keys.

### 4.2 Directory structure

```text
application/cli-proxy-api/container/
|- Containerfile
|- VERSION
`- bin/
   |- cli-proxy-api-render-config
   `- cli-proxy-api-xai-login
```

### 4.3 Containerfile solution

```dockerfile
ARG CLIPROXYAPI_IMAGE=docker.io/eceasy/cli-proxy-api:v7.2.80

FROM ${CLIPROXYAPI_IMAGE}

RUN apt-get update \
    && apt-get install -y --no-install-recommends jq \
    && rm -rf /var/lib/apt/lists/*

COPY --chmod=0755 application/cli-proxy-api/container/bin/ /usr/local/bin/
```

Requirements:

- The upstream base image must use a fixed tag; do not use `latest`.
- Derived images are released to GHCR through the existing `release-container` process of this repository.
- `Containerfile` must not override the upstream `CMD`; the main container still starts CLIProxyAPI directly.
- Scripts must use POSIX shell, run from an absolute path, and not depend on the current working directory.
- The script does not accept keys as command line arguments to avoid appearing in process parameters.
- The image only adds deployment tools; it does not introduce a reverse-proxy sidecar or Kubernetes API client.

### 4.4 forgekit integration

Chart annotation associates derived images with `sshpiper`:

```yaml
annotations:
  cli-proxy-api/images: |
    - name: cli-proxy-api-runtime
      path: application/cli-proxy-api/container
      valuesKey: image.tag
```

Container and chart versions must be managed through `forgekit`; do not edit version fields manually.

## 5. Configuration generation

### 5.1 Configuration layering

The configuration is strictly divided into three layers:

| Layer | Resources | Content | Sensitive |
| --- | --- | --- | --- |
| Baseline Configuration | ConfigMap | host, port, auth-dir, logs, retries, routes, etc. | No |
| Credentials | Secret | CPA API Key List | Yes |
| Final configuration | emptyDir | Complete configuration merged by the init container | Yes |

The Secret does not contain a standalone `config.yaml` file or non-sensitive settings such as host, port, Ingress, and logging.

### 5.2 Secret Contract

Production deployments must pre-create an Opaque Secret:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: <release-name>-credentials
type: Opaque
stringData:
  api-keys: '["<CPA_API_KEY>"]'
```

Here we only define the data structure of Secret and do not write real values in documents, values or Git.

The `api-keys` value is a JSON array of one or more CPA client keys. The init container must verify that:

- The top-level type is an array.
- The array contains at least one element.
- Each element is a non-empty string.
- Terminate Pod startup when validation fails, but do not include key contents in the error message.

The values file stores only the Secret reference and key names:

```yaml
credentials:
  existingSecret: ""
  secretKeys:
    apiKeys: api-keys
```

`credentials.existingSecret` is required by default. The first version does not create Secrets containing inline keys, preventing real keys from entering values or Helm release data.

### 5.3 Non-sensitive values

Deployment boundaries such as host, port, TLS, and the auth directory are not stored in the Secret; some remain fixed:

```yaml
host: ""
port: 8317
auth-dir: /data/auths
tls:
  enable: false
```

Adjustable non-sensitive parameters are controlled by values, for example:

```yaml
config:
  debug: false
  loggingToFile: false
  logsMaxTotalSizeMB: 0
  errorLogsMaxFiles: 10
  usageStatisticsEnabled: false
  requestRetry: 3
  maxRetryCredentials: 0
  maxRetryInterval: 30
  disableCooling: false
  wsAuth: true
  routing:
    strategy: round-robin
    sessionAffinity: false
    sessionAffinityTTL: 1h
  streaming:
    keepaliveSeconds: 15
    bootstrapRetries: 1
  extra: {}
```

`config.extra` is used only for other non-sensitive fields of CLIProxyAPI. The template must prevent it from overriding the following reserved fields:

- `host`
- `port`
- `tls`
- `auth-dir`
- `api-keys`
- `remote-management.secret-key`
- Any provider API Key field

Proxy URLs containing usernames, passwords or tokens cannot be written to `config.extra` either. When you do need more sensitive configuration in the future, you should extend the Secret contract and renderer instead of stuffing the secret into values.

### 5.4 ConfigMap Baseline

The chart renders fixed fields and `.Values.config` to `config-base.json`. Using JSON instead of concatenated YAML lets the init container use `jq` for structured validation and merging.

The baseline configuration contains at least:

```json
{
  "host": "",
  "port": 8317,
  "tls": {
    "enable": false,
    "cert": "",
    "key": ""
  },
  "remote-management": {
    "allow-remote": false,
    "secret-key": "",
    "disable-control-panel": true
  },
  "auth-dir": "/data/auths",
  "api-keys": [],
  "logging-to-file": false,
  "usage-statistics-enabled": false,
  "ws-auth": true
}
```

ConfigMap does not contain any real API Key, OAuth token or TLS private key.

### 5.5 init container synthesis

Pod uses three volumes:

```text
config-base    ConfigMap   -> /input/config/config-base.json (read-only)
credentials    Secret      -> /input/credentials/api-keys  (read-only)
runtime-config emptyDir    -> /runtime                     (read-write)
```

The init container and the main container use the same derived image. The init container runs:

```text
/usr/local/bin/cli-proxy-api-render-config
```

Renderer logic:

1. Read `/input/config/config-base.json`.
2. Use `jq` to verify that `/input/credentials/api-keys` is a legal non-empty string array.
3. Write the API Key array into the `api-keys` field of the baseline configuration.
4. Write the results to a temporary file.
5. Use `jq -e` to validate the final JSON again.
6. Atomically move the result to `/runtime/config.yaml` with `0600` permissions.
7. Do not output final configuration or Secret contents to stdout/stderr.

The main container only mounts:

```text
/runtime/config.yaml -> /CLIProxyAPI/config.yaml
```

The main container does not need to mount the credentials Secret directly. The complete configuration exists only in the Pod's `emptyDir`; it is destroyed with the Pod and regenerated when the next Pod starts.

### 5.6 Configuration changes and Key rotation

- After the ConfigMap content changes, a new Pod needs to be created before the init container will be re-executed.
- After the content of the existing Secret changes, a new Pod needs to be created to generate a configuration containing the new Key.
- Chart-generated ConfigMap uses checksum pod annotation to automatically trigger rollout.
- An external Secret cannot provide a content checksum during Helm rendering; after key rotation, the Secret manager must trigger a rollout or an operator must run `kubectl rollout restart`.
- The chart does not grant the Pod permission to read the Kubernetes API or update the Secret.

## 6. OAuth state and PVC

### 6.1 Why PVC must be used

The OAuth JSON contains the access token, refresh token, ID token, and account identifier. CLIProxyAPI writes the refreshed token back to this file, making it sensitive dynamic state rather than static configuration.

The Kubernetes Secret volume is a read-only projection and cannot hold CLIProxyAPI's runtime refresh writes. The authentication directory must be mounted on a writable PVC:

```text
/data/auths
```

### 6.2 values design

This follows the `codespace` StorageClass and `existingClaim` patterns:

```yaml
persistence:
  auth:
    enabled: true
    storageClass: ""
    existingClaim: ""
    accessModes:
      - ReadWriteOnce
    size: 1Gi
    subPath: ""
    annotations: {}
    labels: {}
    selector: {}
    dataSource: {}
```

Behavior:

- Create a PVC when `enabled: true` and `existingClaim` is not specified.
- Use the cluster default StorageClass when `storageClass: ""` is specified.
- Write `storageClassName` when setting `storageClass`.
- Reuse existing PVC when setting `existingClaim`.
- Use `emptyDir` when `enabled: false`; this is for temporary testing only, and OAuth must be re-established after the Pod is rebuilt.

PVCs contain highly sensitive credentials and should enable storage-side encryption, strict RBAC, and encrypted backups.

## 7. Initial manual OAuth

### 7.1 Entry point

Helm installations do not create hooks or Jobs that await human action. After the Pod starts normally, the operator runs:

```bash
kubectl exec -it \
  --namespace <namespace> \
  deployment/<release-fullname> \
  -- /usr/local/bin/cli-proxy-api-xai-login
```

Script execution in the image:

```bash
/CLIProxyAPI/CLIProxyAPI \
  --xai-login \
  --no-browser \
  --config /CLIProxyAPI/config.yaml
```

### 7.2 Manual steps

1. Read the complete verification URL and device code from the terminal.
2. Log in to the account that actually holds SuperGrok in the browser.
3. Enter the device code and confirm authorization.
4. Keep the terminal connected and wait for the authentication file to be written to `/data/auths`.
5. The login script uses `jq` to idempotently set `using_api: true` in the xAI OAuth file.
6. Confirm that the authentication file exists, but do not output the file content.

values controls the routing compatibility processing required by the current version:

```yaml
xai:
  usingAPI: true
```

The Deployment passes this non-sensitive switch to the login script as an environment variable.

Script requirements:

- Do not print OAuth JSON.
- Do not print access token, refresh token, ID token or API Key.
- Only process `/data/auths/xai-*.json`.
- Use `jq` for structured updates and do not use `sed` to modify JSON.
- Atomic replacement via temporary files and `mv`.
- Keep authentication file permissions at `0600`.
- Even if the CLIProxyAPI login command only logs an error and returns success, determine the final result by checking that the authentication file exists and its JSON fields are valid.

### 7.3 Why not use Helm hook

Device flow requires people to complete browser confirmation within a limited time. Putting it into a Helm hook or automatic job will cause:

- Helm wait timeout.
- Job retries to generate multiple device codes.
- device code and URL entered into centralized log.
- GitOps controller repeatedly rebuilds one-time login resources.
- Coupling one-time account setup failures to every upgrade.

Therefore, explicit `kubectl exec -it` is the only default login path.

## 8. Pod restart and migration

### 8.1 Restart during login process

If the Pod or exec session is interrupted before the device flow completes, the current polling process is terminated. Just re-execute the login script and use the new device code.

### 8.2 Restart after login is completed

After the authentication file is written to the PVC, normal Pod restart does not require device login again:

- Pod names and UIDs do not participate in OAuth file persistence.
- Use the refresh token to refresh the access token automatically after it expires.
- The refreshed token continues to be written back to the same PVC.

### 8.3 Node migration

As long as the StorageClass/CSI driver can unmount the RWO volume from the old node and mount it to the new node, there is no need to log in again after the Deployment migration. A volume's Availability Zone limits and fault recovery capabilities are determined by the StorageClass.

### 8.4 Cross-cluster recovery

When migrating authentication data:

1. First shrink the old environment to `0`.
2. Restore the latest auth PVC data.
3. Maintain file permissions and directory ownership.
4. Start the new environment and perform minimal model calls.
5. Restart device login only when the refresh token expires, the session is revoked, or the backup is too old.

The old and new environments cannot use the same copied refresh token state at the same time, otherwise token rotation competition and old token replay may occur.

## 9. Deployment and replica strategy

Workloads use `Deployment`:

- The service does not rely on stable Pod names or network identities.
- Persistent state is provided by a separate PVC.
- Consistent with `codespace`'s Deployment + PVC mode.

Default configuration:

```yaml
replicas: 1
updateStrategy:
  type: Recreate
```

The file-based OAuth token store is single-writer. A single replica and `Recreate` avoid:

- Both Pods refresh and overwrite the refresh token at the same time.
- RWO PVC multi-mount waits during a rolling upgrade.
- The operations login script selecting different Pods.

`_helpers.tpl` must verify `replicas == 1`. In the future, multiple replicas will only be considered after switching and verifying the external storage of CLIProxyAPI.

## 10. Fixed application port

CLIProxyAPI's internal listening port is fixed at `8317`. The values schema does not define application-port or Service-port fields.

Ports are defined once in `_helpers.tpl`:

```gotemplate
{{- define "cli-proxy-api.port" -}}8317{{- end -}}
```

This helper is uniformly referenced in the following locations:

- ConfigMap's `port`.
- Deployment's `containerPort`.
- TCP probes.
- Service's `port` and `targetPort`.
- Service port of Ingress backend.

Service uses `ClusterIP` by default. External access is entirely handled by Traefik Ingress.

## 11. Traefik Ingress

### 11.1 Design Principles

The Ingress template is based directly on `application/sub2api/chart/templates/ingress.yaml`:

- Use standard Kubernetes `Ingress`.
- Use `common.capabilities.ingress.apiVersion`.
- Use `common.ingress.backend`.
- Merge `ingress.annotations` and `commonAnnotations`.
- Support `hostname`, `path`, `pathType`, `extraHosts`, `extraPaths`, `extraRules`, and `extraTls`.
- Point the backend to the ClusterIP Service on fixed port `8317`.

Traefik listens to standard Ingress resources through the Kubernetes Ingress provider. TLS can be handled by the user's existing Traefik entryPoint, certificate resolver, Ingress annotations, or `spec.tls`.

### 11.2 values draft

```yaml
ingress:
  enabled: false
  ingressClassName: traefik
  hostname: cli-proxy-api.example.internal
  path: /
  pathType: Prefix
  annotations: {}
  tls: false
  tlsSecret: ""
  extraHosts: []
  extraPaths: []
  extraTls: []
  extraRules: []
```

The chart only renders a standard Ingress and user-provided Traefik annotations/TLS references. It does not create TLS Secrets or assume a particular Traefik entryPoint or certificate-management method.

Users set annotations and TLS according to their Traefik environment. For example, if the environment selects entryPoint or certificate resolver through annotations, write `ingress.annotations` directly; if using an existing TLS Secret, set `ingress.tls` and `ingress.tlsSecret`.

### 11.3 SSE and WebSocket

CLIProxyAPI's SSE and WebSocket traffic is forwarded through the standard HTTP Service. The chart does not include controller-specific timeout objects; if the environment requires a Traefik Middleware, ServersTransport, or another CRD, configure it through:

- `ingress.annotations`
- `ingress.extraRules`
- `extraDeploy`

Traefik Kubernetes Ingress Reference:

- <https://doc.traefik.io/traefik/providers/kubernetes-ingress/>
- <https://doc.traefik.io/traefik/reference/routing-configuration/kubernetes/ingress/>

## 15. Template responsibilities

### `configmap.yaml`

- Render fixed configuration and `.Values.config` to `config-base.json`.
- Use structured Helm dict/toJson to assemble sensitive values without string replacement.
- Does not contain the actual content of `api-keys`.
- Excludes OAuth data and TLS data.

### `deployment.yaml`

- Call `cli-proxy-api.validateValues`.
- Use common rendering names, tags, images, affinity, securityContext and resources.
- Run the init container and main container using the same derived image.
- The init container mounts ConfigMap, credentials Secret and runtime emptyDir.
- The main container only mounts the generated runtime config and auth PVC.
- Configure ConfigMap checksum into pod annotations.
- Expose fixed named port `http: 8317`.
- Use TCP startup/readiness/liveness probes by default to prevent HTTP paths with authentication from affecting the probes.
- Supports custom probes, extra env Secrets, extra mounts and extra volumes.

### `service.yaml`

- Default `ClusterIP`.
- Service `port` and `targetPort` fixed to `8317`.
- Use the same annotation merge and selector merge modes as `sshpiper`/`sub2api`.
- Service type and common extension fields are retained, but port values are not provided.

### `ingress.yaml`

- Direct reference to `sub2api` Ingress template.
- backend Service port uses fixed port helper.
- Default `ingressClassName: traefik`.
- Support for users with existing TLS and Traefik annotations.
- Does not create or manage certificates.

### `auth-pvc.yaml`

- Mimics `codespace` PVC fields.
- Only created if `enabled=true` and `existingClaim` is empty.

### `NOTES.txt`

- Give the first `kubectl exec -it` device login command.
- Gives the Secret structure requirements, but does not read or output the Secret contents.
- Note that the credentials Secret requires a rollout after rotation.
- Gives a command to check whether the auth file exists, but does not output the file contents.
- Does not output CPA API Key, OAuth token or TLS information.

### `extra-list.yaml`

Consistent with `sshpiper`, `codespace`, `sub2api`, use `common.tplvalues.render` to render `extraDeploy`.

## 16. Security context

The goal is to run the init container, main container and exec login script with UID/GID `1001`:

- Credentials Secret volume uses `defaultMode: 0440`.
- Pod `fsGroup: 1001` provides Secret read-only permissions and PVC write permissions to the init container.
- runtime config created with UID `1001` and set to `0600`.
- auth JSON created with UID `1001` and set to `0600`.
- Drop all Linux capabilities.
- Disable privilege escalation.

The implementation phase must verify that the upstream base image can run CLIProxyAPI and device login as a non-root user. If the pinned image depends on root, adjust the default securityContext based on the verification results and record the reason; do not break the service merely to claim non-root execution.

## 17. Installation and first-time activation sequence

1. Prepare namespace.
2. Generate one or more CPA API Keys on site.
3. Create a credentials Secret containing only the `api-keys` field.
4. Confirm the default StorageClass, or set `persistence.auth.storageClass`/`existingClaim`.
5. Complete the Ingress hostname, annotations, and TLS configuration as per your existing Traefik environment.
6. Install the chart.
7. init container generates a complete configuration and the main container starts.
8. Wait for TCP probes to be ready.
9. Execute `kubectl exec -it ... cli-proxy-api-xai-login`.
10. Complete device verification manually.
11. Confirm that xAI JSON is present in the auth PVC, but do not output the content.
12. Call `/v1/models` using CPA API Key.
13. Execute `grok-4.5` minimal text request.
14. Optional verification `grok-build-0.1`; the image generation test is only executed when the credit consumption is accepted.

## 18. Security and Backup

- The credentials Secret contains only the API key and no ordinary configuration.
- The complete generated configuration is stored in the Pod's `emptyDir` and is destroyed with the Pod.
- OAuth PVC is protected at the same level as Secret.
- Remote management and control panel are turned off by default.
- Keep native TLS disabled and terminate TLS at Traefik.
- Use `ClusterIP` for the Service by default.
- Do not grant the application ServiceAccount permission to read the Secret API or modify cluster resources.
- Do not output credentials in logs, NOTES, probes, or operations scripts.
- Use a snapshot-capable StorageClass and encrypt auth PVC backups where possible.
- Stop the old instance before restoring to avoid refreshing the same token in both environments at the same time.

## 22. Final recommendations

Implement the first version of chart according to this plan:

- Maintain a lightweight derived image based on the upstream fixed version.
- Built-in configuration renderer and xAI login script in the image.
- The Secret stores only the API key, while all common configuration is controlled by values.
- The init container synthesizes the complete configuration, and the main container only reads the generated results.
- OAuth tokens are persisted on a PVC with a single writer.
- The first device login is triggered explicitly by a human.
- Application port is fixed to `8317`.
- Outbound access and TLS are completely left to the user's existing Traefik Ingress.
- The chart structure fully reuses bitnami common and follows the repository patterns used by `sshpiper`, `codespace`, and `sub2api`.
